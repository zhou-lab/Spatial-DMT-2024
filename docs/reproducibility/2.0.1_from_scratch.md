# Spatial-DMT 2.0.1 clean-room reproducibility audit

## Scope

This audit tested release tag `2.0.1` as a new user would encounter it: a
fresh clone, a fresh Micromamba prefix, profile setup based on `README.md`, and
new run directories that did not reuse previous pipeline outputs. The two
end-to-end tests were:

| Protocol | Test sample | Reference | Modalities | Input |
|---|---|---|---|---:|
| Spatial-DMT | `SpHSK05DMT19` | hg38 | DNA | 1,000,000 read pairs |
| SmC-seq | `E65_10um_run1_200k` | mm10 | DNA + RNA | 200,000 DNA and 200,000 RNA read pairs |

The test used existing shared hg38, mm10, Lambda, and STAR reference resources,
which are normal site prerequisites in the documented profile. It did not test
construction of those references from source FASTA/GTF files. All specialized
pipeline dependencies, including YAME, BISCUIT/`bsconv`, the vendored native
tools, and BBTools, were installed or built in the new scratch space.

Test host: Zhou Lab Slurm cluster, `defq`

### Documented dependency command

The dependency set in `README.md` was attempted without substitutions:

```bash
micromamba create -y -p "$ENV" -c conda-forge -c bioconda \
  snakemake=9.19.0 star=2.7.11b biscuit=1.8 \
  samtools=1.22.1 htslib=1.22.1 bedtools=2.31.1 \
  dupsifter=1.3.0 yame=1.9 pigz=2.8 parallel=20260422 \
  multiqc r-base r-seurat biopython fuzzysearch regex pysam \
  matplotlib pandas
```

This command did not solve. There were two independent causes:

1. No `yame=1.9` build was available in the configured channels; the current
   available release was 1.10.
2. The available `dupsifter=1.3.0` builds required older `libdeflate` versions
   that conflicted with the version required by the current `biscuit=1.8`
   build.

The workflow already vendors and builds its modified dupsifter, so the conda
dupsifter package is redundant. The successful clean environment used YAME
1.10 and omitted conda dupsifter:

```bash
micromamba create -y -p "$ENV" -c conda-forge -c bioconda \
  snakemake=9.19.0 star=2.7.11b biscuit=1.8 \
  samtools=1.22.1 htslib=1.22.1 bedtools=2.31.1 \
  yame=1.10 pigz=2.8 parallel=20260422 \
  multiqc r-base r-seurat biopython fuzzysearch regex pysam \
  matplotlib pandas
export PATH="$ENV/bin:$PATH"
python -m pip install snakemake-executor-plugin-cluster-generic
```

### Vendored native programs

The workflow auto-builds its vendored dupsifter, BAM splitter, and CpG-to-YAME
converter. Their tagged Makefiles default to this lab-only HTSlib source tree:

```text
/mnt/isilon/zhoulab/labsoftware/samtools/samtools-1.17/htslib-1.17
```

That makes the nominal automatic build depend on software outside the fresh
environment. `HTSLIB_ROOT` can be overridden, but the Makefiles expect a source
tree layout (`HTSLIB_ROOT/htslib` and `HTSLIB_ROOT/libhts.a`), whereas a conda
prefix uses `include/htslib` and `lib/libhts.a`. A compatibility root was made
without modifying tracked source files:

```bash
mkdir -p "$ROOT/htslib_root"
ln -s "$ENV/include/htslib" "$ROOT/htslib_root/htslib"
ln -s "$ENV/lib/libhts.a" "$ROOT/htslib_root/libhts.a"

COMMON_LIBS="-L$ENV/lib -Wl,-rpath,$ENV/lib \
  -lbz2 -ldeflate -lm -lpthread -lz -llzma"

make -C "$ROOT/repo/tools/dupsifter_speed" clean
make -C "$ROOT/repo/tools/dupsifter_speed" \
  HTSLIB_ROOT="$ROOT/htslib_root" CLIB="$COMMON_LIBS"

make -C "$ROOT/repo/tools/split_bam_by_cb_hts" clean
make -C "$ROOT/repo/tools/split_bam_by_cb_hts" \
  HTSLIB_ROOT="$ROOT/htslib_root" LDLIBS="$ROOT/htslib_root/libhts.a $COMMON_LIBS"

make -C "$ROOT/repo/tools/cpg_to_yame" clean
make -C "$ROOT/repo/tools/cpg_to_yame" \
  HTSLIB_ROOT="$ROOT/htslib_root" \
  LDLIBS="$ROOT/htslib_root/libhts.a $COMMON_LIBS -lpthread"
make -C "$ROOT/repo/tools/cpg_to_yame" test \
  HTSLIB_ROOT="$ROOT/htslib_root"
```

`cpg_to_yame` tests passed, and `ldd` confirmed that the generated programs use
libraries from the fresh environment rather than the hidden lab HTSlib tree.

### SmC-seq

Deterministic 200,000-pair prefixes were made with `pigz` from published
SmC-seq E6.5 run-1 DNA and matching RNA deliveries:

```bash
RUN="$ROOT/runs/smcseq"
SAMPLE=E65_10um_run1_200k
DEST="$RUN/fastq/$SAMPLE"
mkdir -p "$DEST"

DNA=/scr1/users/suc3/spatial-5mc-embryo-decidua-reproduce/data/CRR1678214
RNA=/scr1/users/suc3/spatial-5mc-embryo-decidua-reproduce/data/CRR1678224

for mate in 1 2; do
  pigz -dc "$DNA/CRR1678214_r${mate}.fq.gz" \
    | head -n 800000 | pigz -p 8 > "$DEST/DNA_${mate}.fq.gz"
  pigz -dc "$RNA/CRR1678224_r${mate}.fq.gz" \
    | head -n 800000 | pigz -p 8 > "$DEST/RNA_${mate}.fq.gz"
done
```

All four subset files passed `gzip -t`; each had 800,000 lines and paired read
names agreed between mates.

## Execution

An attempted local Spatial-DMT run completed trimming but the interactive
process was killed while BISCUIT loaded hg38 at approximately 4.2 GiB RSS. This
was an interactive-session cgroup limit, not a malformed input or workflow
failure. Both production tests were therefore executed through the documented
Slurm profile. Capacity was checked first; the account limit at submission was
146 CPUs and 1,807 GiB, with no existing allocation.

The tests deliberately used an eight-CPU workflow ceiling:

```bash
COMMON_CONFIG=(
  "YAME=$ENV/bin/yame"
  "DNA_TRIM_CPUS=8" "DNA_TRIM_OVERHEAD_CPUS=2"
  "DNA_ALIGN_CPUS=8" "DNA_ALIGN_SORT_CPUS=4" "DNA_ALIGN_MEM=32G"
  "DNA_PILEUP_CPUS=8" "DNA_PILEUP_MEM=32G"
  "LAMBDA_ALIGN_CPUS=4" "LAMBDA_ALIGN_SORT_CPUS=2" "LAMBDA_PILEUP_MEM=16G"
  "UNMATCHED_ALIGN_CPUS=8" "UNMATCHED_SORT_CPUS=4" "UNMATCHED_ALIGN_MEM=32G"
  "UNMATCHED_DIAGNOSTICS_CPUS=4"
)
```

Spatial-DMT command:

```bash
cd "$ROOT/runs/spatialdmt"
snakemake --profile "$ROOT/profile_slurm" \
  --snakefile "$ROOT/repo/main/Snakefile" \
  --cores 8 --jobs 2 \
  --resources cpus_per_task=8 mem_mb=256000 \
  --rerun-incomplete \
  --config ref=hg38 "${COMMON_CONFIG[@]}"
```

SmC-seq command:

```bash
cd "$ROOT/runs/smcseq"
snakemake --profile "$ROOT/profile_slurm" \
  --snakefile "$ROOT/repo/main/Snakefile" \
  --cores 8 --jobs 2 \
  --resources cpus_per_task=8 mem_mb=256000 \
  --rerun-incomplete \
  --config ref=mm10 protocol=smcseq "${COMMON_CONFIG[@]}"
```

The commands did not override `DNA_TRIM_MEM`, so the trim jobs requested the
tagged default of 160 GiB. This fit the account limit but is much larger than a
small test requires. The copied Slurm profile's `latency-wait: 100` was needed:
some completed-job outputs took tens of seconds to become visible on shared
storage, and Snakemake then continued normally.

The RNA rule runs `module load STAR` whenever the shell exposes the module
function. On this cluster that replaced the fresh environment's STAR 2.7.11b
with the site-provided STAR 2.7.10b. This is compatible with the stated
assumption that standard aligners may already be site-provided, but it means
the documented tested STAR version does not control a Slurm run on a
module-enabled host.

## Results and validation

Both runs completed the default `final_output` target. All 29 Slurm jobs
submitted by the two production invocations finished with state `COMPLETED` and
exit code 0. The controller wall times were 27:28 for the Spatial-DMT resume
after local trimming and 1:03:17 for the full SmC-seq Slurm run.

Deliverable directories:

```text
/scr1/users/suc3/spatial_dmt_2.0.1_repro_20261016/runs/spatialdmt/final_output/SpHSK05DMT19
/scr1/users/suc3/spatial_dmt_2.0.1_repro_20261016/runs/smcseq/final_output/E65_10um_run1_200k
```

Each contains the sample and Lambda `.cg` files, YAME index, self-contained QC
report, MultiQC report and data, and `pipeline_version.tsv`. The SmC-seq bundle
also contains the STARsolo `Solo.out` gene-expression matrices.

Key execution checks, reported only to demonstrate that real data traversed the
intended branches, were:

| Check | Spatial-DMT | SmC-seq |
|---|---:|---:|
| Raw DNA pairs | 1,000,000 | 200,000 |
| DNA structure/whitelist-pass reads | 72,345 | 162,303 |
| Indexed spatial columns in `.cg` | 2,480 | 8,189 |
| `bsconv -m 2` retained | not applicable | 127,065 / 164,549 (77.22%) |
| RNA reads entering STAR | not applicable | 132,581 |
| STAR unique mapping | not applicable | 21.04% |
| STARsolo estimated cells | not applicable | 6,019 |

These values reflect deliberately small test inputs and are not intended as
biological or production-quality benchmarks.

Validation included:

- `pigz -t` on all input and generated compressed FASTQs;
- `samtools quickcheck` on all generated BAMs, including 8,189 SmC-seq
  barcode BAMs;
- `yame info` on sample and Lambda containers;
- existence and content checks for QC and MultiQC HTML reports;
- STARsolo raw and filtered matrix checks;
- exact release metadata checks (`2.0.1`, protocol, and reference);
- repeat Snakemake dry-runs, both reporting that all requested files were
  present and up to date.

The SmC-seq post-run dry-run warned that the three manually rebuilt native
programs lacked Snakemake provenance metadata. That is expected because they
were rebuilt explicitly to avoid the private default HTSlib path; it did not
schedule any work. The clean release clone had no tracked source differences.

The trim process emitted `free(): invalid pointer` / `munmap_chunk(): invalid
pointer` messages from a child process after GNU Parallel completed. The rule
returned zero, all expected partition FASTQs were present, gzip validation
passed, and record counts agreed with the trim statistics. The same messages
were observed in the local attempt, so this is reproducible and should be
investigated even though it did not corrupt these test outputs.

MultiQC 1.35 also reported that the `--cl-config` YAML string generated by the
rule could not be parsed. MultiQC still produced a complete report and found
the custom, BBMap, and BISCUIT inputs, but the requested sample-name replacement
and BISCUIT column-visibility customization were ignored.

For SmC-seq, the 200,000-pair subset populated 8,189 of 9,216 barcode columns.
Consequently, the per-cell pileup took 23:27, the first whole-container YAME
aggregation took 16:50, and the report's second YAME aggregation took 9:40.
This is valid behavior but shows that small-test runtime scales strongly with
nonempty barcode count and reference-wide aggregation, not only input reads.

Result: 7 tests passed.

## Problems encountered

| Severity | Observation | Classification | Workaround used |
|---|---|---|---|
| Blocking | Documented conda specification cannot solve (`yame=1.9`; dupsifter/libdeflate conflict) | Documentation/release environment defect | YAME 1.10; omit redundant conda dupsifter |
| Blocking | Vendored native-tool Makefiles default to a private HTSlib source tree | Portability defect | Explicit fresh-environment HTSlib compatibility root and rebuild |
| Blocking | Snakefile defaults YAME to a private absolute path | Portability defect | Pass `YAME=$ENV/bin/yame` on every invocation |
| Blocking outside this lab | Reference construction is not documented | Documentation gap | Use the configured shared references |
| Minor | Linux BBTools section gives a product page but no archive command | Documentation gap | Official SourceForge 39.81b archive |
| Site-specific | Local BISCUIT process was killed by the interactive cgroup | Cluster policy, not pipeline logic | Run through Slurm |
| Site-specific | Shared-storage output visibility was delayed | Filesystem behavior | Existing `latency-wait: 100` handled it |
| Non-blocking | `rna_star_solo` unconditionally prefers a loadable STAR module; this cluster supplied 2.7.10b instead of the documented 2.7.11b | Environment-precedence defect | Run completed with the common site aligner; record its actual version |
| Non-blocking | Trim emitted allocator warnings in both local and Slurm execution despite valid outputs and exit status 0 | Runtime defect requiring follow-up | Validate gzip/read partitions and downstream BAMs |
| Non-blocking | MultiQC 1.35 rejected the generated `--cl-config` YAML | Report customization defect | Report still generated; sample renaming/column hiding was not applied |
| Performance | Curated metrics and HTML reporting each rescan the full YAME container | Workflow optimization opportunity | Allow both documented scans to finish |

## Current conclusion

The release source completed both protocol DAGs and produced valid DNA-only and
DNA+RNA deliverables from a fresh software prefix. Tag `2.0.1` is nevertheless
not reproducible from the README alone without intervention: the conda command
is unsatisfiable, YAME and native HTSlib defaults leak private site paths, and
reference construction is unspecified. The tested processing logic completed;
the release still needs environment, path, and documentation fixes before it
can be described as independently reproducible from its public instructions.
